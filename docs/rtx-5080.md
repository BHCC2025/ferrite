# Ferrite on the NVIDIA RTX 5080

Ferrite also serves Qwen3.8-27B on a single **RTX 5080** (16 GB, compute capability 12.0). It is the same engine as on
DGX Spark: the same Rust kernels, compiled to PTX for `sm_120a` instead of `sm_121a`, the same scheduler and server.
What changes is where things live, because a 16 GB card cannot hold what a Spark's unified memory does:

- the **EXL3 3.0 bpw decode weights** stay on the card (about 10 GB with the output head);
- the **K/V cache** is stored as 6-bit records instead of bf16, so 128K tokens take 3.7 GB instead of 9.1 GB;
- the **NVFP4/FP8 prompt weights** (16.8 GB) stay in pinned host memory and visit the card one layer at a time while
  the prompt is processed;
- the **embedding table** and the **prompt cache's pool** are in host memory;
- drafting is the model's own **MTP head with copy rows** (the DFlash2 drafter does not fit beside the weights).

> **Status: experimental.** One model, one card, built from source only, on Linux. One request at a time by default,
> or up to four from a shared pool of context ([Several requests at once](#several-requests-at-once)). It was
> developed and measured on a single machine.

## Results

One RTX 5080 in a desktop with a 24-core CPU, 62 GB of memory and a PCIe 5.0 x16 slot. Qwen3.8-27B, EXL3 3.0 bpw
mix, greedy decoding, fixed prompts (`tools/bench`), 128K context configured, thinking off. Tokens per second, medians
of 3 runs after a warm-up.

| | Ferrite on one RTX 5080 |
|---|---|
| Code, 2K context | 304 |
| Prose, 2K context (clean replies) | 121 |
| Code edits, 500 tokens (rename / type hints) | 688 / 409 |
| Code edits, whole file (rename / type hints) | 778 / 392 |
| Plain decoding, no speculation | 62 |
| Prompt processing, 2K / 16K / ~120K context | ~5,320 / ~4,060 / ~2,150 |
| KL divergence vs BF16 (code / text / 16K context / 120K context), lower is better | 0.0207 / 0.0427 / 0.0230 / 0.0056 |
| The same with a bf16 K/V cache (32K context), code / text / 16K context | 0.0206 / 0.0399 / 0.0235 |
| Device memory, 128K context: at load / peak | 15.2 GiB / 15.3 GiB of 15.9 |

- The 6-bit K/V cache moves KL by a few percent either way. Most of the text set's difference comes from one of its
  20 sequences; the other 19 are within about 2% of the bf16 cache's figure.
- Prompt processing is the time to the first token over HTTP: it includes the MTP head's pass over the prompt and the
  prompt cache's snapshots.
- The prose figure counts only replies that do not fall into echoing the prompt, which the benchmark's prose prompt
  tends to cause under greedy decoding (2 echoed and 1 partly of 12 seeds here; `tools/bench/README.md`).
- Speculative decoding is lossless: with drafting off the server gives the same text, token for token
  (checked on ten requests: code, prose, a 16K prompt, four file edits of up to 1,500 tokens, a two-turn conversation with thinking, a tool call). A turn resumed from the prompt cache gives the text of the full computation.
- A 5-fact needle test over a 120K-token prompt found 5 of 5. A 30-minute soak of agent-style conversations with tool
  calls (@SOAK@) finished without an error.

## Requirements

- An RTX 5080 (16 GB). Other RTX 50 cards have the same compute capability but were not tried: launch geometry and the
  tuned decode plans are the 5080's (84 SMs), and less than 16 GB does not hold the weights with a useful context.
- NVIDIA driver 580 or later (tested with 595.99), a PCIe slot at full width (the prompt weights cross it for every
  prompt chunk: 16.8 GB a pass).
- About 40 GB of free host memory: 16.8 GB of pinned prompt weights, the embedding table (2.4 GB) and the prompt
  cache's pool (8 GB by default).
- About 34 GB of disk for the two model folders.
- To build: stable Rust 1.99+, the kernels' pinned nightly (`nightly-2026-11-04`, `kernels/rust-toolchain.toml`) with
  `rust-src`, `llvm-tools`, `llvm-bitcode-linker` and the `nvptx64-nvidia-cuda` target, and `ptxas` from the CUDA 13
  toolkit (tested with 13.3). No libibverbs or NCCL: the two-node fabric is only linked on the Spark build.

## Build

```bash
git clone https://github.com/BHCC2025/ferrite && cd ferrite
FE_KARCH=sm_120a scripts/check-deps.sh --build --install
FE_KARCH=sm_120a cargo build --release -p fe-server --features ferrite -p fe-cli
FE_KARCH=sm_120a scripts/check-deps.sh          # the card, the driver, the linked libraries
target/release/ferrite selftest                 # every kernel family against host math, on the card
```

`FE_KARCH` picks the kernel architecture at build time (default `sm_121a`, the DGX Spark): the kernels are compiled
with that `target-cpu` and assembled with `ptxas -arch` of the same name, in their own target directory
(`kernels/target-sm_120a`), so both builds can live in one checkout.

## Serve

```bash
tools/serve-5080.sh                             # http://0.0.0.0:8000/v1, model id "spark" (FERRITE_MODEL_ID)
curl -s localhost:8000/v1/models
```

Loading takes about half a minute once the files are in the page cache. `FERRITE_HOST=127.0.0.1` keeps the server
local (there is no API key, so firewall it otherwise). `tools/serve-5080.sh --help` prints the resolved settings; the
preset's defaults:

| Variable | Default | What it sets |
|---|---|---|
| `CTX` / `FERRITE_CTX` | `131072` | Context length. The K/V cache takes 28 KB a token at 6 bits. |
| `SLOTS` / `FERRITE_SLOTS` | `1` | Requests at once; more wait in a queue. Two slots need half the context each. |
| `FE_KVQ` | `6` | Bits a value of the K/V cache: `6`, or `4` (0.8 GB less at 128K; KL about 4-8% higher and more echoing on the prose benchmark), or `0` for bf16 (a 32K context then). |
| `DRAFT`, `SPEC`, `COPY` | `mtp`, `8`, `47` | MTP drafts a round and the most copy rows a round. `SPEC=0 COPY=0` turns drafting off. |
| `PROMPT` | `fp4` when the NVIDIA checkpoint is there | `fp4`, or `bf16` (here: the EXL3 weights on the decode kernels). |
| `CHUNK` | `2240` | Prompt rows a forward: 35 blocks of 64 rows fill the card's 84 SMs in whole waves of attention blocks. |
| `FE_PROMPT_RING` | `2` | Layers of prompt weights on the card at once (0.26 GB each). |
| `CACHE`, `PARK_GB` | `1`, `8` | The prompt cache and its pool in host memory. |
| `FE_CACHE_LEAD_MIN` | `4096` | Prompts this long are saved at the last whole chunk before each turn boundary, so the next turn of a long conversation resumes there instead of processing the prompt again (0 = off). |

The small-memory forms can also be set one by one (`FE_LOWMEM=0` turns them all off, the default on a device with 40
GB or more): `FE_EMBED_HOST`, `FE_KVQ`, `FE_PROMPT_STREAM`, `FE_MTP_BF16`, `FE_PARK_HOST`, `FE_CACHE_MTP`.

## How it fits and where the speed comes from

- **A 6-bit K/V cache, read without rotating keys back.** Every K and V head vector is rotated by a block Hadamard
  (32 dims a group), each group is scaled by its maximum, and the values are stored as 6-bit codes: 208 bytes a head
  instead of 512. Q is rotated the same way, so Q.K is unchanged; P.V is summed in the rotated basis and the output
  row is rotated back once. Tiles are dequantized into shared memory as they are loaded and feed the same
  tensor-core code as the bf16 cache. For prompt rows four extra warps of each block do that while the other four
  run the tensor cores, which hides the cost. KL against BF16 is the bf16 cache's; the scheme is exllamav3's cache
  quantization in a record layout of Ferrite's own (kernels/k-core/src/kvq.rs).
- **Prompt weights from host memory.** Each layer's NVFP4/FP8 codes and scales are one pinned blob. A second stream
  copies layer N + 1 into a two-slot ring on the card while layer N computes; a slot is rewritten only after its
  layer finished. One pass moves 16.8 GB and takes about as long as the computation it feeds.
- **FP8 GEMMs on the block-scaled tensor-core form.** On this card the plain FP8 `mma` runs at half the rate of the
  block-scaled one. With every scale set to 1 the block-scaled form gives the same bits (`fp4-check` compares them),
  so the FP8 projections use it.
- **Decode plans for 84 SMs.** The EXL3 GEMV's splits and warps per shape were tuned on the card (`exl3-tune`,
  crates/fe-exl3/src/plans.rs): 16.0 ms a token without speculation, against 18.6 ms with the DGX Spark's plans. Decode
  attention uses one block an SM for each segment's four K/V heads.
- **MTP drafts and copy rows in one verify tree.** The MTP head drafts a chain; a copy of earlier text is grafted
  onto it where they agree and branches where they part. Code edits, which mostly repeat the file they were shown,
  verify 32 to 48 rows a round. Every verify row is bitwise the row plain decoding would compute, which is what keeps
  the reply the same.
- **A prompt cache that works with the MTP head.** The head's K/V rows are parked and restored with the model's;
  snapshots and parked conversations live in host memory and cross the bus in a few milliseconds.

## Limits

- One request at a time by default; a second slot halves the context of each.
- A prompt chunk of more than 16 rows streams every layer's prompt weights once (about a third of a second), so a
  turn's time to first token has that floor.
- At very long contexts decode attention is the larger part of a step: about 20 ms a round at 120K.
- The DFlash2 drafter and the two-node mode are DGX Spark only.

## Several requests at once

`SLOTS=4 tools/serve-5080.sh` serves up to four requests at once from one pool of context (`FE_POOL=1`, set by the
preset): four units of 28,160 tokens. A request that fits a unit with its reply runs beside others. A longer one, up
to 112,640 tokens, takes the whole pool and runs alone: the others wait in the queue, and conversations in its way are
parked in host memory and resumed later. `/health` reports `max_batch_size` 4 and `max_model_len` 112640. Requests
that arrive together and start with the same text have that prefix computed once.

The preset uses 15 copy rows a sequence and a 2048-row prompt chunk, which leaves about 0.1 GiB of the card free
under load (four units of 32K do not fit beside the weights).

N streaming requests sent together, sharing a prefix of P tokens, 800 tokens of code each (`tools/bench/lanes.py`,
medians of 3 sets after a warm-up):

| Requests | Shared prefix | Total tokens/s | Tokens/s a request | Time for the set | Prompt tokens computed |
|---|---|---|---|---|---|
| 1 | 2K | 134 | 134 | 6.0 s | 2,156 |
| 2 | 2K | 236 | 122 | 6.8 s | 2,319 of 4,323 |
| 4 | 2K | 385 | 100 | 8.3 s | 2,684 of 8,696 |
| 1 | 16K | 86 | 86 | 9.3 s | 16,150 |
| 2 | 16K | 150 | 76 | 10.7 s | 16,322 of 32,309 |
| 4 | 16K | 236 | 59 | 13.6 s | 16,707 of 64,668 |

The text of each request equals the text of the same request sent alone (checked at 1, 2 and 4 requests, with a
follow-up round), and a 68K-token request and its second turn give the text of the one-slot preset.

A lone request against the one-slot preset: code 288 tokens/s (305), 500-token edits 504 / 330 (691 / 411, which has
47 copy rows), prompt processing ~5,330 / ~4,480 tokens/s at 2K / 16K (~5,320 / ~4,070).
