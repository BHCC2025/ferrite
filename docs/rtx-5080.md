# Ferrite on the NVIDIA RTX 5080 and RTX 5060 Ti (16 GB)

Ferrite serves **Qwen3.8-27B** on a single 16 GB card, an **RTX 5080** or an **RTX 5060 Ti 16 GB**, behind an
OpenAI-compatible API on port 8000, with a context of up to 128K tokens.

- **Speed.** On the RTX 5080: code at 298 tokens/s, prose at 119, code edits at up to 692, prompts at about 5,340
  tokens/s ([Results](#results)). On the RTX 5060 Ti: code at 157 tokens/s
  ([On an RTX 5060 Ti 16 GB](#on-an-rtx-5060-ti-16-gb)).
- **What you need.** The card, NVIDIA driver 580 or later, about 40 GB of free host memory, about 34 GB of disk for
  the models, Linux ([Requirements](#requirements)).
- **How you get it.** Built from source: [Run it](#run-it) has the commands.
- An RTX PRO 4000 Blackwell (24 GB) has its own preset and page: [rtx-pro-4000.md](rtx-pro-4000.md).

The terms used on this page (K/V cache, copy rows, MTP, slots, `sm_120a`) are explained in
[Words used in these docs](../README.md#words-used-in-these-docs).

> **Status: experimental.** One model, one card, built from source only, on Linux. One request at a time by default,
> or up to four from a shared pool of context ([Several requests at once](#several-requests-at-once)). It was
> developed and measured on a single machine.

## Requirements

| | |
|---|---|
| Card | An RTX 5080 (16 GB) or an RTX 5060 Ti 16 GB. Launch geometry and the tuned decode plans are the 5080's (84 SMs); the 5060 Ti (36 SMs) has a decode-plan table of its own. Less than 16 GB does not hold the weights with a useful context. Other 16 GB RTX 50 cards were not tried. |
| Card memory | 128K of context needs about 15.3 GiB of the card's 15.9. When the card also drives your desktop, the display takes some of it and the server starts with a shorter context ([Context and the card's memory](#context-and-the-cards-memory)). |
| Driver | NVIDIA driver 580 or later (tested with 595.99). |
| PCIe slot | A slot at full width: the prompt weights cross it for every prompt chunk, 16.8 GB a pass. |
| Host memory | About 40 GB free: 16.8 GB of pinned prompt weights, the embedding table (2.4 GB) and the prompt cache's pool (8 GB by default). Before loading, the launcher checks that about 30 GB is available with the defaults (20 GB for the prompt weights, the pool, and 2 GB) and stops with the numbers if not. |
| Disk | About 34 GB for the two model folders, and about 3 GB more for a build (the Rust toolchains and the target directory). Put the models on a disk with room: `FERRITE_MODELS` (the default `/var/tmp/models` is on the root disk). |
| Operating system | Linux, x86_64; tested on Ubuntu 24.04. |
| Build tools | The system packages, `ptxas` (`cuda-nvcc-13-x`) and cuBLASLt (`libcublas-dev-13-x`) from NVIDIA's CUDA repository, and rustup: [quickstart.md, Clean machine](quickstart.md#clean-machine) has the commands for a fresh Ubuntu 24.04 or 26.04 (both tested in clean containers). Then stable Rust 1.99+ and the kernels' pinned nightly (`nightly-2026-11-04`, `kernels/rust-toolchain.toml`), which `scripts/check-deps.sh --build --install` installs. No libibverbs or NCCL: the two-node fabric is only linked on the Spark build. |

**Cooling.** Ferrite keeps a card at full load for as long as requests come in. Cards in adjacent slots heat each
other, so give a machine with two or more cards enough case airflow and watch their temperature under a long run
(`nvidia-smi --query-gpu=temperature.gpu --format=csv -l 5`). A card that overheats can crash the driver or keep
the machine from booting until it has cooled.

## Run it

### 1. Build

```bash
git clone https://github.com/BHCC2025/ferrite && cd ferrite
FE_KARCH=sm_120a scripts/check-deps.sh --build --install
FE_KARCH=sm_120a cargo build --release -p fe-server --features ferrite -p fe-cli
FE_KARCH=sm_120a scripts/check-deps.sh          # the card, the driver, the linked libraries
target/release/ferrite selftest                 # every kernel family against host math, on the card
```

About `FE_KARCH`:

- It picks the kernel architecture at build time: `sm_121a` for the DGX Spark, `sm_120a` for RTX 50 cards. The
  kernels are compiled with that `target-cpu` and assembled with `ptxas -arch` of the same name, in their own target
  directory (`kernels/target-sm_120a`).
- Without `FE_KARCH` the build takes the card `nvidia-smi` reports, so on the machine with the card it can be left
  out.
- A binary built for another card stops before anything loads, with the rebuild command: the launchers,
  `scripts/check-deps.sh` and `fe-server` itself check it.
- `target/release/fe-server` holds one build. To keep the Flash-Next engine ([flash-next.md](flash-next.md)) in the
  same checkout, build both into one binary with `--features ferrite,fnext`.

### 2. Download the models

```bash
python3 -m venv ~/.venvs/hf && ~/.venvs/hf/bin/pip install -U huggingface_hub
export FERRITE_MODELS=$HOME/models
scripts/fetch-models.sh quant prompt            # about 34 GB, sha256-checked
```

| Role | Repository | License |
|---|---|---|
| Decode weights: EXL3 mixed 3.0 bpw (5-bit head), with the MTP head | [`BHCC2025/Qwen3.8-27B-EXL3-3.0bpw-mix`](model-card.md) | Apache-2.0 |
| Prompt weights: NVFP4/FP8 | [`nvidia/Qwen3.8-27B-NVFP4`](https://huggingface.co/nvidia/Qwen3.8-27B-NVFP4) | Apache-2.0 |

Without the NVIDIA checkpoint (or with `PROMPT=bf16`) the prompt goes through the EXL3 weights on the decode kernels:
about 1,200 tokens per second instead of several thousand, and no host memory for prompt weights.

### 3. Start the server

```bash
tools/serve-5080.sh                             # http://<this machine>:8000/v1, model id "qwen3.8-27b" (FERRITE_MODEL_ID)
```

- The same launcher serves both cards. On an RTX 5080 or RTX 5060 Ti, `scripts/serve.sh` starts this preset by
  itself; on an RTX PRO 4000 Blackwell it starts [the PRO 4000 preset](rtx-pro-4000.md).
- It runs in the foreground, and its process becomes the server: Ctrl-C or `kill <pid>` stops it.
- Loading takes about half a minute once the files are in the page cache (longer the first time, while they are
  read from the disk).
- The server listens on every interface, so other machines on your network can use it, and there is no API key: use
  it on a trusted network or firewall the port. `FERRITE_HOST=127.0.0.1` keeps it local.
- `tools/serve-5080.sh --help` lists the settings. Everything of `scripts/serve.sh` applies.

### 4. Test it

```bash
curl -s localhost:8000/v1/models
curl -s http://127.0.0.1:8000/v1/chat/completions -H 'content-type: application/json' \
  -d '{"model":"qwen3.8-27b","messages":[{"role":"user","content":"Say hello in five words."}],"max_tokens":200}'
```

Thinking is on by default in the Qwen template, so part of a small `max_tokens` goes to the reasoning. Add
`"chat_template_kwargs": {"enable_thinking": false}` to the request to turn it off. Client and sampling settings:
[model-card.md, Recommended settings](model-card.md#recommended-settings) and [harness.md](harness.md).

### 5. Run it in the background, stop it, read the log

```bash
scripts/ferritectl.sh start rtx                 # starts tools/serve-5080.sh in the background and waits until /health answers
scripts/ferritectl.sh status                    # running or not, and /health
scripts/ferritectl.sh log                       # the log (log -f follows it)
scripts/ferritectl.sh stop                      # stops it and waits until the card is free
```

The log is `<ferrite folder>/logs/server-8000.log` (the previous run's is kept as `.log.1`; `FERRITE_LOG_DIR` moves
it). A server started by hand with `tools/serve-5080.sh` writes to its terminal.

## Settings

The short names below are the same settings as their `FERRITE_*` forms.

**Settings you may want to change:**

| Variable | Default | What it sets |
|---|---|---|
| `CTX` / `FERRITE_CTX` | the most that fits, up to `131072` | Context length ([below](#context-and-the-cards-memory)). The K/V cache takes 28 KB a token at 6 bits. |
| `SLOTS` / `FERRITE_SLOTS` | `1` | Requests at once (slots), 1-4 ([Several requests at once](#several-requests-at-once)); more wait in a queue. |
| `DRAFT` / `FERRITE_DRAFT`, `SPEC`, `COPY` | `mtp`, `8`, `47` | MTP drafts a round and the most copy rows a round. `DRAFT=off` (or `SPEC=0 COPY=0`) turns drafting off: plain decoding. |
| `PROMPT` | `fp4` when the NVIDIA checkpoint is there | `fp4`, or `bf16` (here: the EXL3 weights on the decode kernels). |
| `FE_KVQ` | `6` | Bits a value of the K/V cache: `6`, or `4` (0.8 GB less at 128K; KL about 4-8% higher and more echoing on the prose benchmark), or `0` for bf16 (68 KB a token: about 55K fits, and the preset picks that by itself). |
| `CACHE`, `PARK_GB` | `1`, `8` | The prompt cache and its pool in host memory. |
| `FERRITE_VRAM_RESERVE_MIB` | `128` (`768` with a display) | Card memory left free when the context is sized. |
| `FERRITE_HOST`, `FERRITE_PORT`, `FERRITE_MODEL_ID` | `0.0.0.0`, `8000`, `qwen3.8-27b` | Listen address, port and the model id the API reports. |

**Tuning variables (leave at their defaults unless you are measuring):**

| Variable | Default | What it sets |
|---|---|---|
| `CHUNK` | `2240` | Prompt rows a forward: 35 blocks of 64 rows fill the card's 84 SMs in whole waves of attention blocks. |
| `FE_PROMPT_RING` | `2` | Layers of prompt weights on the card at once (0.26 GB each). |
| `FE_GDN_OVERLAP` | on with fewer than 48 SMs | In a prompt group, the next chunk's GDN projection runs beside the current chunk's recurrence (`0` = off, `1` = on). |
| `FE_PROMPT_GROUP` | on | Long prompts run their chunks layer by layer, so the prompt weights cross the bus once a group (`0` = off; a number = the most rows a group holds). |
| `FE_CACHE_LEAD_MIN` | `4096` | Prompts this long are saved at the last whole chunk before each turn boundary, so the next turn of a long conversation resumes there instead of processing the prompt again (0 = off). |

The small-memory forms can also be set one by one (`FE_LOWMEM=0` turns them all off, the default on a device with 40
GB or more): `FE_EMBED_HOST`, `FE_KVQ`, `FE_PROMPT_STREAM`, `FE_MTP_BF16`, `FE_PARK_HOST`, `FE_CACHE_MTP`.

### Context and the card's memory

**How the context is chosen.** At start the preset reads the card's free memory and picks the longest context that
fits, up to 128K, keeping 128 MiB free for other programs (768 MiB when the card drives a display;
`FERRITE_VRAM_RESERVE_MIB` sets it). On an empty card that is 128K: the model takes about 12,000 MiB of the card
(the weights, the MTP head, workspaces and the ring of prompt weights) and 128K of 6-bit K/V cache 3.5 GiB (3.7
GB). The K/V cache takes 28 KB a token at 6 bits (`FE_KVQ=4`: 19 KB, so more fits), so each 8K of context is about
0.22 GB of the card. A `FERRITE_CTX` that cannot fit is refused before loading, with the numbers.

**When a desktop uses the card.** When a desktop holds part of the card, the launcher says so in its output (the
terminal, or the log under `ferritectl.sh`) and starts with less, for example `the card has 15100 MiB free (with
768 MiB kept for the display and other programs): context 86272 instead of 131072`.

## Several requests at once

`SLOTS=4 tools/serve-5080.sh` serves up to four requests at once from one pool of context (`FE_POOL=1`, set by the
preset).

- **Slot, unit, pool.** A slot is one request the server works on at a time. With `SLOTS` above 1 the slots share
  one pool of context, cut into units, one a slot. A unit holds up to 28,160 tokens and is sized to the card's free
  memory at start like the one-slot context: on an otherwise empty 16 GB card that is 27,392 tokens a unit, with
  128 MiB kept free, and the pool is four of them (109,568 tokens).
- A request that fits a unit with its reply runs beside others.
- A longer one, up to the whole pool, takes it all and runs alone: the others wait in the queue, and conversations
  in its way are parked in host memory and resumed later.
- `/health` reports `max_batch_size` 4 and the pool as `max_model_len`.
- Requests that arrive together and start with the same text have that prefix computed once.
- The preset uses 15 copy rows a sequence and a 2048-row prompt chunk; four units of 32K do not fit beside the
  weights.

N streaming requests sent together, sharing a prefix of P tokens, 800 tokens of code each, on an otherwise empty
5080 (units of 27,392 tokens; `python3 tools/bench/lanes.py --lanes 1,2,4 --prefix 2000,16000 --runs 3` against
`SLOTS=4 tools/serve-5080.sh`, medians of 3 sets after a warm-up). "Total tokens/s" is every request's generated
tokens over the wall time of the whole set, prompt processing included, so the one-request rows read lower than the
decode speed in [Results](#results):

| Requests | Shared prefix | Total tokens/s | Tokens/s a request | Time for the set | Prompt tokens computed |
|---|---|---|---|---|---|
| 1 | 2K | 141 | 141 | 5.7 s | 2,156 |
| 2 | 2K | 241 | 121 | 6.6 s | 2,318 of 4,321 |
| 4 | 2K | 383 | 101 | 8.4 s | 2,683 of 8,692 |
| 1 | 16K | 89 | 89 | 9.0 s | 16,152 |
| 2 | 16K | 146 | 74 | 10.9 s | 16,328 of 32,315 |
| 4 | 16K | 233 | 59 | 13.7 s | 16,718 of 64,676 |

The text of each request equals the text of the same request sent alone (`lanes.py --gate --seed 7`: 1, 2 and 4
requests, with a follow-up round), and a 68K-token request and its second turn give the text of the one-slot preset.

A lone request on the 4-slot preset against the one-slot preset (measured with 28,160-token units): code 288
tokens/s (one-slot 298), 500-token edits 504 / 330 (692 / 411; the one-slot preset has 47 copy rows), prompt
processing ~5,330 / ~4,480 tokens/s at 2K / 16K (~5,340 / ~4,400).

decoding, thinking off. Tokens per second, medians of 3 runs. Measured 2026-11-14 with Ferrite 0.6.0; not
re-measured since.

|---|---|
| Code, 2K context | 298 |
| Prose, 2K context (clean replies) | 119 |
| Code edits, 500 tokens (rename / type hints) | 692 / 411 |
| Code edits, whole file (rename / type hints) | 784 / 395 |
| Plain decoding, no speculation | 62 |
| Prompt processing, 2K / 16K / ~120K context | ~5,340 / ~4,400 / ~2,160 |

- Switching to the 6-bit K/V cache changes KL by a few percent in either direction. Most of the text set's
  difference comes from one of its 20 sequences; the other 19 are within about 2% of the bf16 cache's figure.
- Prompt processing is the time to the first token over HTTP: it includes the MTP head's pass over the prompt and the
  prompt cache's snapshots.
- "Clean replies": the benchmark's prose prompt tends to make a greedy reply echo the prompt, and the prose figure
  counts only the replies that do not. Of the 12 seeds tried here, 2 replies echoed the prompt and 1 did so partly

- Speculative decoding is lossless: with drafting off the server gives the same text, token for token. This was
  checked on ten requests: code, prose, a 16K prompt, four file edits of up to 1,500 tokens, a two-turn conversation
  with thinking, and a tool call. A turn resumed from the prompt cache gives the text of the full computation.
- A 5-fact needle test over a 120K-token prompt found 5 of 5. A 30-minute soak of agent-style conversations with tool
  calls finished without an error.
- To reproduce, start `tools/serve-5080.sh` and run:
  - code: `QB_SEED=1 python3 tools/bench/quickbench.py --mode code --tokens 500 --context 2000 --runs 3`;
  - prose: `--mode prose` with `QB_SEED` 1 to 6, the median of the replies it marks clean;

    stream 0 is the rename, stream 1 the type hints);
  - prompt processing: `--mode code --tokens 16 --context 2000` (16000, 120000), the prompt line;
  - plain decoding: the code command against `DRAFT=off tools/serve-5080.sh`.

## Limits

- One request at a time by default. With `SLOTS` 2 to 4 each request gets a unit of up to 28,160 tokens from a
  shared pool instead of the one-slot context ([Several requests at once](#several-requests-at-once)).
- A prompt chunk of more than 16 rows streams every layer's prompt weights once (about a third of a second on the
  5080), so a turn's time to first token has that floor.
- At very long contexts decode attention is the larger part of a step: about 20 ms a round at 120K.
- The DFlash2 drafter is not part of this preset: it does not fit beside the weights on a 16 GB card (it runs on
  the DGX Spark and on the Arc Pro B70). The two-node mode is DGX Spark only.

## Troubleshooting

The launcher checks the binary, the port, the GPU lock, the model files and the memory before it loads the model,
and stops with a message that names the problem:

- `... was built for sm_121a, but this GPU ... needs sm_120a` (from the launcher or `scripts/check-deps.sh`): the
  binary was built for another card. Rebuild with the `FE_KARCH` the message names ([Build](#1-build)).
- `port 8000 is already in use (by ...)`: another server has the port. Stop it, or set `FERRITE_PORT`.
- `another Ferrite GPU job holds ... (...)`: a Ferrite server or job is already running on that card; the message
  names the lock and its holder. Stop it (`scripts/ferritectl.sh stop`, or `kill` the pid named), or wait for it
  with `FERRITE_LOCK_WAIT=1`.
- `only N GB of host memory is available; the RTX preset needs about M GB`: free host memory, or lower `PARK_GB`.
- `the card has N MiB free; ... even an 8K context does not fit`: close what else uses the card (`nvidia-smi`), or
  set `FE_KVQ=4`.
- `FERRITE_CTX=N does not fit the card`: lower `FERRITE_CTX`, or set `FE_KVQ=4`; the message gives the most that
  fits.
- `the model folders do not match scripts/models.manifest`: a model file is missing or cut off. Run
  `scripts/fetch-models.sh quant prompt` again.
- `FERRITE_DRAFT=dflash: the DFlash2 drafter does not fit beside the weights on a 16 GB card`: use `mtp` (the
  default) or `off`.
- A reply is empty or cut short with a small `max_tokens`: thinking is on by default ([Test it](#4-test-it)).

`FERRITE_FORCE=1` starts despite a failed memory or model-file check. More, written for the DGX Spark:
[quickstart.md, Troubleshooting](quickstart.md#troubleshooting).

## How it fits and where the speed comes from

It is the same engine as on DGX Spark: the same Rust kernels, compiled to PTX for `sm_120a` (compute capability
12.0) instead of `sm_121a`, the same scheduler and server. What changes is where things live, because a 16 GB card
cannot hold what a Spark's unified memory does:

- the **EXL3 3.0 bpw decode weights** stay on the card (about 10 GB with the output head);
- the **K/V cache** is stored as 6-bit records instead of bf16, so 128K tokens take 3.7 GB instead of 9.1 GB;
- the **NVFP4/FP8 prompt weights** (16.8 GB) stay in pinned host memory and visit the card one layer at a time while
  the prompt is processed;
- the **embedding table** and the **prompt cache's pool** are in host memory;
- drafting is the model's own **MTP head with copy rows** (the DFlash2 drafter does not fit beside the weights).

In more detail:

- **A 6-bit K/V cache, read without rotating keys back.** Every K and V head vector is rotated by a block Hadamard
  (32 dims a group), each group is scaled by its maximum, and the values are stored as 6-bit codes: 208 bytes a head
  instead of 512. Q is rotated the same way, so Q.K is unchanged; P.V is summed in the rotated basis and the output
  row is rotated back once. Tiles are dequantized into shared memory as they are loaded and feed the same
  tensor-core code as the bf16 cache. For prompt rows four extra warps of each block do that while the other four
  run the tensor cores, which hides the cost. KL against BF16 is the bf16 cache's; the scheme is exllamav3's cache
  quantization in a record layout of Ferrite's own (kernels/k-core/src/kvq.rs).
- **Prompt weights from host memory.** Each layer's NVFP4/FP8 codes and scales are one pinned blob. A second stream
  copies layer N + 1 into a two-slot ring on the card while layer N computes; a slot is rewritten only after its
  layer finished. One pass moves 16.8 GB and takes about as long as the computation it feeds.
- **A long prompt crosses the bus once a group, not once a chunk.** A prompt that is alone on the card runs its
  next chunks layer by layer: every chunk through layer 0, then every chunk through layer 1, and so on, with each
  layer's weights fetched once for all of them. Every (layer, chunk) is the launch sequence the chunk's own forward
  would enqueue, in the same order, so the K/V cache, the GDN state and every row's bits are the same. The chunks'
  hidden states wait on the card (10 KB a row), so a group takes what memory is free. Where a chunk ends on a
  snapshot point of the prompt cache, each GDN layer's state is kept as the layer passes it, and the snapshot stores
  that; a cancelled request stops the group between layers. On the 5080 the bus keeps up with the
  computation and this gives a few percent; on a card with a narrower link it is most of the prompt time
  ([the RTX 5060 Ti](#the-rtx-5060-ti-in-detail)). `FE_PROMPT_GROUP=0` turns it off.
- **FP8 GEMMs on the block-scaled tensor-core form.** On this card the plain FP8 `mma` runs at half the rate of the
  block-scaled one. With every scale set to 1 the block-scaled form gives the same bits (`fp4-check` compares them),
  so the FP8 projections use it.
- **Decode plans for 84 SMs.** The EXL3 GEMV's splits and warps per shape were tuned on the card (`exl3-tune`,
  crates/fe-exl3/src/plans.rs): 16.0 ms a token without speculation, against 18.6 ms with the DGX Spark's plans. Decode
  attention uses one block an SM for each segment's four K/V heads.
- **MTP drafts and copy rows in one verify tree.** The MTP head drafts a chain; a copy of earlier text is grafted
  onto it where they agree and branches where they part. Code edits, which mostly repeat the file they were shown,
  verify 32 to 48 rows a round. Every verify row is bitwise the row plain decoding would compute, which is what keeps
  the reply the same.
- **A prompt cache that works with the MTP head.** The head's K/V rows are parked and restored with the model's;
  snapshots and parked conversations live in host memory and cross the bus in a few milliseconds.

### The RTX 5060 Ti in detail

The decode plans have a table of their own for the card's 36 SMs (`exl3-tune`, crates/fe-exl3/src/plans.rs: 27.4 ms
a token over the model's linears against 31.0 with the DGX Spark's plans).

A pass of the prompt weights takes longer than on the 5080: 2.4 s on the 4-lane link (1.2 s at x8), whatever the
chunk holds. Prompt groups (above) make that one pass a group instead of one a chunk, which leaves the card's own
computation as the limit: about twice the prompt speed with the default chunk, in the memory that is free anyway. A
turn of more than 16 new tokens still pays one pass (2.4 s on the 4-lane link) before its first token: in a
10-minute soak of agent-style conversations with tool calls (135 requests, no error) the median time to first token

With the link out of the way the prompt is bound by the card's computation. At 16K the time goes to the MLP (about a
third), the GDN recurrence and attention (a fifth each) and the GDN projections; at 56K attention is half of it. Per
SM that is the 5080's rate. Two things are particular to 36 SMs: the NVFP4 GEMMs take the mbarrier pipeline here
(the same bits, the MLP 17% faster: `FE_FP4_KERNEL` picks another), and the chunked GDN kernel's 48 head blocks need
two waves of 36, the second with 12 blocks. In a prompt group the next chunk's input norm and GDN projection start
on a second stream as the recurrence is launched, so they take the SMs the second wave leaves idle and the chunk
finds its projection done: the same kernels on the same inputs, about 5% of a 16K prompt (`FE_GDN_OVERLAP=0` turns
it off; it is on where a card has fewer SMs than the model has GDN value heads).
